# 관리자 회원·시험 관리 제품 계획

## 1. 문서 목적과 현재 전제

이 문서는 초기 Next.js 16.3 프로젝트에서 먼저 구현할 관리자 경험의 범위, 우선순위, 사용자 흐름, 데이터 계약, 수용 기준을 정의한다. 구현자가 별도 제품 결정을 하지 않아도 P0 데모를 만들고, 이후 Elysia·Neon PostgreSQL·Drizzle ORM 기반 실데이터로 교체할 수 있는 수준을 목표로 한다.

현재 저장소는 `src/app` 기반 App Router 기본 템플릿이며 실제 회원·시험 데이터, 인증, API, 데이터베이스, shadcn/ui, Motion 의존성이 없다. `package.json`에는 `dev`, `build`, `start`, `lint` 스크립트만 있고 패키지 관리자는 Bun 1.3.11이다. 따라서 이 문서의 P0는 **관리자 화면과 결정론적 데모 데이터 계약**까지이며, 실서비스 인증·영속화·문항 저작·응시 기능은 별도 단계로 본다.

### 제품 가정

- 주 사용자는 운영 관리자이며 데스크톱에서 다수의 회원과 시험을 빠르게 조회·관리한다.
- P0 데모에서는 단일 `관리자` 권한으로 모든 화면과 동작을 노출한다.
- 운영 언어와 날짜 표시는 한국어, `Asia/Seoul`, `YYYY.MM.DD HH:mm`을 기본으로 한다.
- 회원 탈퇴와 시험 보관은 복구 및 감사 가능성을 위해 소프트 상태 변경으로 다룬다.
- 간편 등록은 시험 메타데이터를 빠르게 만드는 기능이다. 문항 작성·CSV 업로드·문항 은행 연결은 포함하지 않는다.
- 데모 변경은 브라우저 세션 안에서만 유지될 수 있으며 새로고침 시 초기화될 수 있다. 이 제약은 화면에 명시한다.

## 2. 목표, 비목표, 성공 기준

### 목표

1. 관리자가 회원을 검색·필터링하고 상세 정보를 확인하며 이용 상태를 안전하게 바꿀 수 있다.
2. 관리자가 시험을 검색·필터링하고 상태와 일정을 파악하며 상세 정보를 확인할 수 있다.
3. 관리자가 최소 필드만 입력해 임시 시험을 만들고 곧바로 시험 목록에서 결과를 확인할 수 있다.
4. 모든 주요 화면이 로딩·빈 결과·오류·권한 부족·잘못된 입력을 설명하고 복구 경로를 제공한다.
5. UI가 데모 데이터 소스를 직접 알지 않도록 계약을 분리해 실데이터 전환 비용을 낮춘다.

### 비목표

- 수험자용 시험 응시, 답안 제출, 채점, 결과 통지
- 문항 저작기, 문항 은행, 엑셀·CSV 일괄 등록, 파일·이미지 업로드
- 회원 생성, 비밀번호 재설정, 이메일·SMS 발송, 결제·조직 관리
- 관리자 계정·역할 관리와 세분화된 RBAC 설정 UI
- 실시간 공동 편집, 감사 로그 조회 화면, 대규모 내보내기
- P0 단계의 Elysia REST API, Neon 연결, Drizzle 스키마·마이그레이션

### 성공 기준

- 첫 방문 사용자가 별도 안내 없이 3분 이내 회원 1명을 찾고, 시험 1개를 간편 등록할 수 있다.
- P0의 모든 명시적 수용 기준과 QA 체크리스트가 통과한다.
- 키보드만으로 검색, 필터, 행 상세 진입, 상태 변경, 간편 등록을 완료할 수 있다.
- 데모 데이터 모듈을 교체해도 페이지·컴포넌트의 표시 계약을 변경할 필요가 없다.

## 3. 범위와 우선순위

| 우선순위 | 범위 | 포함 이유 | 완료 정의 |
| --- | --- | --- | --- |
| P0 | 관리자 공통 셸, 회원 목록·상세, 시험 목록·상세, 시험 간편 등록, 데모 데이터, 모든 기본 UI 상태 | 핵심 운영 흐름을 처음부터 끝까지 검증 | 이 문서의 P0 수용 기준과 QA 통과 |
| P1 | `/admin` 요약, 회원·시험 페이지네이션, 시험 수정, 시험 상태 변경, URL 기반 필터 유지, 제한적 역할(`운영자`, `조회자`) | 운영 효율과 재방문성을 높임 | 권한별 동작과 영속 URL 검증 |
| P2 | 문항 저작·일괄 등록, 감사 로그, 대량 작업, 내보내기, 알림, 분석 지표 | 실제 운영 규모와 컴플라이언스 대응 | 별도 PRD 및 데이터 모델 승인 |

P0에서 상태 변경 UI는 제품 규칙 검증을 위해 포함하되, 데모 환경에서는 세션 한정 변경으로 동작한다. P1 실데이터 연결 전에는 운영 데이터가 변경된다는 인상을 주지 않도록 `데모 모드` 배지와 초기화 안내를 항상 노출한다.

### 권장 URL

| URL | 화면 | P0 |
| --- | --- | --- |
| `/admin` | `/admin/members`로 이동; P1에서 요약 화면으로 대체 가능 | 포함 |
| `/admin/members` | 회원 목록, 검색, 상태 필터 | 포함 |
| `/admin/members/[memberId]` | 회원 상세와 상태 변경 | 포함 |
| `/admin/exams` | 시험 목록, 검색, 상태 필터 | 포함 |
| `/admin/exams/new` | 시험 간편 등록 | 포함 |
| `/admin/exams/[examId]` | 시험 상세 | 포함 |

App Router의 중첩 레이아웃으로 `/admin` 공통 셸을 공유한다. 페이지와 레이아웃은 기본 Server Component로 유지하고, 검색 입력의 즉시 반응, 모바일 메뉴, 확인 대화상자, 폼 상태처럼 상호작용이 필요한 최소 단위만 Client Component로 둔다. 목록 검색·필터는 `searchParams`를 기준으로 서버에서 처리할 수 있는 계약을 우선하며, P0 데모 구현이 클라이언트 필터를 쓰더라도 같은 쿼리 이름을 유지한다.

## 5. 전역 사용자 경험 규칙

### 탐색과 피드백

- 현재 메뉴는 색상뿐 아니라 굵기·배경·`aria-current="page"`로 식별한다.
- 각 페이지에는 고유한 문서 제목과 하나의 설명적인 `h1`이 있어야 한다. Next.js 경로 알림이 문서 제목, `h1`, URL 순으로 읽는 동작을 고려한다.
- 주요 작업 성공 시 토스트 또는 인라인 상태로 무엇이 바뀌었는지 알리고, 화면 데이터도 즉시 일치시킨다.
- 제출·상태 변경 중에는 해당 버튼만 비활성화하고 진행 문구를 노출한다. 전체 화면을 불필요하게 막지 않는다.
- 목록 조건은 `q`, `status`, 향후 `page` 쿼리로 표현해 새로고침·공유·뒤로 가기 동작을 예측 가능하게 만든다.

### 위험 작업

- 회원 정지·탈퇴 처리, 시험 보관은 확인 대화상자를 거친다.
- 대화상자는 대상 이름, 현재 상태, 변경 상태, 사용자 영향, 되돌릴 수 있는지 여부를 표시한다.
- 확인 버튼에는 `확인` 대신 `김민준 회원 정지`, `시험 보관`처럼 결과가 분명한 동사를 사용한다.
- 동일 요청의 중복 제출을 막고, 실패 시 원래 상태를 유지하며 재시도 경로를 제공한다.

### 데이터 표시

- 식별자가 긴 경우 화면에서는 축약할 수 있지만 복사 가능한 전체 값을 상세에 제공한다.
- 날짜가 없으면 `-` 대신 의미가 있는 `미설정`, `응시 이력 없음`을 사용한다.
- 상태는 색상만으로 구분하지 않고 항상 텍스트 배지를 함께 사용한다.
- 정렬은 P0에서 회원 `가입일 최신순`, 시험 `수정일 최신순`으로 고정하고 현재 정렬 기준을 목록 설명에 알린다.

## 6. 역할과 권한

P0는 단일 관리자 역할만 구현하지만, 표시와 서비스 계약은 향후 역할 확장을 막지 않아야 한다.

| 역할 | 회원 조회 | 회원 상태 변경 | 시험 조회 | 시험 등록·수정 | 시험 상태 변경 |
| --- | --- | --- | --- | --- | --- |
| 관리자(P0) | 가능 | 가능 | 가능 | 가능 | 가능 |
| 운영자(P1) | 가능 | 제한적으로 가능 | 가능 | 가능 | 가능 |
| 조회자(P1) | 가능 | 불가 | 가능 | 불가 | 불가 |

권한 검사는 메뉴 숨김만으로 끝내지 않는다. 실데이터 단계에서 Data Access Layer(DAL), Elysia 핸들러 또는 Server Action 가까이에서 세션과 역할을 재검증해야 한다. Server Action과 Route Handler는 직접 요청 가능한 공개 엔드포인트와 같은 수준으로 취급한다. 레이아웃만의 권한 검사는 부분 렌더링과 직접 진입을 완전히 보호하지 못하므로 단독 방어선으로 사용하지 않는다.

## 7. 회원 관리

### 7.1 회원 목록

#### 사용자 목적

관리자는 이름·이메일·회원 번호로 회원을 찾고, 상태를 좁혀 최근 가입자와 이용 제한 대상을 빠르게 식별한다.

#### 화면 구성

- 헤더: `회원 관리`, 전체 건수, 기능 설명
- 검색: 이름·이메일·회원 번호 통합 검색, 300~500ms 디바운스 또는 제출 버튼
- 필터: `전체`, `활성`, `정지`, `탈퇴`
- 결과 요약: 현재 조건과 결과 건수, `필터 초기화`
- 목록 열: 회원, 이메일, 상태, 가입일, 최근 로그인, 응시 횟수, 상세 작업
- 행 선택 또는 `상세 보기`로 회원 상세 진입
- P1: 페이지 크기 20, 페이지네이션

모바일에서는 표를 억지로 축소하지 않고 회원별 카드 목록으로 전환한다. 카드에는 이름·이메일·상태·가입일을 우선 표시하고, 최근 로그인과 응시 횟수는 보조 영역에 둔다.

#### 주요 흐름

1. 관리자가 `/admin/members`에 진입한다.
2. 기본 목록이 가입일 최신순으로 표시된다.
3. 검색어 또는 상태 필터를 적용한다.
4. 결과 요약이 갱신되고 조건은 URL 또는 동등한 화면 상태로 유지된다.
5. 원하는 회원의 상세로 이동한다.

### 7.2 회원 상세와 상태 변경

#### 화면 구성

- 뒤로 가기: 이전 목록 조건을 유지한 `회원 목록`
- 요약: 이름, 이메일, 상태, 회원 번호, 가입일
- 기본 정보: 연락처, 최근 로그인, 응시·합격 횟수
- 최근 응시 내역: 시험명, 응시일, 점수, 결과; P0는 최대 5건
- 관리 작업: `활성으로 복구`, `회원 정지`, `탈퇴 처리` 중 가능한 작업만 표시

#### 상태와 전이

| 상태 | 의미 | 허용 전이 | 제한 |
| --- | --- | --- | --- |
| `ACTIVE` | 로그인·응시 가능 | `SUSPENDED`, `WITHDRAWN` | 없음 |
| `SUSPENDED` | 운영자에 의해 이용 정지 | `ACTIVE`, `WITHDRAWN` | 로그인·새 응시 불가 |
| `WITHDRAWN` | 탈퇴 처리된 보존 레코드 | 없음(P0) | 읽기 전용, 개인정보 정책은 실데이터 단계 결정 |

정지 시 P0에서는 사유를 필수로 받지 않지만 확인 화면에 선택 입력으로 제공한다. 실데이터 전환 시 변경자, 변경 시각, 사유를 감사 데이터로 기록해야 한다. 탈퇴 처리의 보존·익명화 규칙은 법무·운영 결정 전까지 실제 기능을 활성화하지 않는다.

## 8. 시험 관리

### 8.1 시험 목록

#### 사용자 목적

관리자는 시험의 공개·진행 상태와 일정을 확인하고, 필요한 시험 상세 또는 간편 등록으로 이동한다.

#### 화면 구성

- 헤더: `시험 관리`, 전체 건수, `시험 간편 등록` 주요 버튼
- 검색: 시험명·시험 코드 통합 검색
- 필터: `전체`, `임시 저장`, `게시 예정`, `진행 중`, `종료`, `보관`
- 목록 열: 시험명/코드, 운영 상태, 응시 기간, 제한 시간, 문항 수, 응시자 수, 수정일, 상세 작업
- 상태 계산 설명 툴팁: 게시 상태와 현재 시간이 결합되어 `게시 예정·진행 중·종료`가 결정됨
- P1: 페이지네이션, 수정, 상태 변경 작업 메뉴

모바일 카드는 시험명·상태·기간·문항 수를 우선 노출하고 나머지 지표를 접을 수 있는 보조 정보로 둔다.

### 8.2 시험 상세

- 요약: 시험명, 시험 코드, 운영 상태, 설명
- 설정: 분류, 제한 시간, 문항 수, 합격 점수, 공개 범위, 응시 기간
- 운영 정보: 응시자 수, 생성일, 수정일
- 문항 영역: P0에서는 `문항 편집은 다음 단계에서 제공됩니다` 안내와 계획된 문항 수만 표시
- P1 작업: 수정, 게시, 종료, 보관
- 없는 ID는 전용 `찾을 수 없음` 화면을 제공하고 시험 목록으로 돌아갈 수 있어야 한다.

### 8.3 시험 상태 모델

영속 상태와 화면 파생 상태를 구분한다.

| 구분 | 값 | 의미 |
| --- | --- | --- |
| 영속 `lifecycleStatus` | `DRAFT` | 작성 중이며 수험자에게 노출되지 않음 |
| 영속 `lifecycleStatus` | `PUBLISHED` | 게시 승인됨; 일정에 따라 화면 상태 계산 |
| 영속 `lifecycleStatus` | `ARCHIVED` | 운영 종료 후 보관; 읽기 전용 |
| 파생 `displayStatus` | `DRAFT` | 영속 상태가 `DRAFT` |
| 파생 `displayStatus` | `SCHEDULED` | `PUBLISHED`이고 시작 전 |
| 파생 `displayStatus` | `OPEN` | `PUBLISHED`이고 시작 이상 종료 이하 |
| 파생 `displayStatus` | `CLOSED` | `PUBLISHED`이고 종료 후 |
| 파생 `displayStatus` | `ARCHIVED` | 영속 상태가 `ARCHIVED` |

P0 간편 등록 결과는 항상 `DRAFT`로 생성한다. 게시 전에는 최소 1개 이상의 실제 문항과 유효한 일정이 필요하지만, 문항 기능이 없는 P0에서는 게시 동작을 활성화하지 않는다.

## 9. 시험 간편 등록

### 9.1 사용자 흐름

1. 관리자가 시험 목록의 `시험 간편 등록`을 선택한다.
2. 단일 페이지 폼에서 기본 정보와 운영 설정을 입력한다.
3. 클라이언트 기본 검증과 서버 계약 검증을 통과한다.
4. 관리자가 `임시 저장`을 선택한다.
5. 중복 제출을 막는 진행 상태가 표시된다.
6. 성공하면 새 시험 상세로 이동하고 `임시 시험이 저장되었습니다`를 알린다.
7. 목록으로 돌아가면 새 시험이 수정일 최신순 첫 결과에 나타난다.

P0에서는 의도치 않은 데이터 손실을 막기 위해 값이 변경된 상태에서 목록으로 이동할 때 이탈 확인을 제공한다. 브라우저 종료까지 완전한 임시 복구는 P1 이후로 둔다.

### 9.2 폼 필드와 기본값

| 섹션 | 필드 | 필수 | 기본값 | 입력/검증 |
| --- | --- | --- | --- | --- |
| 기본 정보 | 시험명 | 예 | 없음 | 1~100자 |
| 기본 정보 | 시험 코드 | 예 | 제안값 또는 없음 | 대문자·숫자·하이픈 3~20자, 중복 불가 |
| 기본 정보 | 분류 | 예 | `기타` | P0: `직무`, `자격`, `교육`, `기타` |
| 기본 정보 | 설명 | 아니오 | 빈 값 | 최대 500자, 글자 수 표시 |
| 운영 설정 | 제한 시간 | 예 | 60분 | 정수 5~300 |
| 운영 설정 | 계획 문항 수 | 예 | 20개 | 정수 1~200 |
| 운영 설정 | 합격 점수 | 예 | 60점 | 정수 0~100 |
| 운영 설정 | 공개 범위 | 예 | 비공개 | P0 선택값은 저장하되 게시하지 않음 |
| 운영 설정 | 응시 시작 | 아니오 | 빈 값 | 종료와 한 쌍, 서울 시간으로 입력 |
| 운영 설정 | 응시 종료 | 아니오 | 빈 값 | 시작보다 늦어야 함 |

### 9.3 검증과 오류 배치

- 필수값 누락, 범위 위반, 날짜 역전은 제출 전에 필드 가까이에 표시한다.
- 시험 코드 중복처럼 데이터 소스 확인이 필요한 오류는 서버 응답을 해당 필드에 연결한다.
- 상단 오류 요약은 오류 개수와 각 필드로 이동하는 링크를 제공한다.
- 첫 오류 필드로 포커스를 이동하되 사용자가 입력 중일 때는 갑자기 이동시키지 않는다.
- 예상 가능한 검증 실패는 예외를 던지기보다 구조화된 결과로 반환한다.
- 알 수 없는 저장 실패는 입력값을 보존하고 전역 오류와 `다시 시도`를 제공한다.

## 10. 핵심 시나리오와 명시적 수용 기준

### 시나리오 A: 활성 회원 검색

- Given 활성·정지·탈퇴 회원을 포함한 데모 데이터가 있다.
- When 관리자가 회원 관리에서 상태 `활성`을 선택하고 이름 일부를 검색한다.
- Then 이름·이메일·회원 번호 중 검색어와 일치하며 상태가 `ACTIVE`인 회원만 표시된다.
- And 결과 건수와 적용 조건이 보이고 `필터 초기화`가 동작한다.
- And 검색 결과가 0건이면 전체 데이터가 없다는 문구가 아니라 조건별 빈 결과가 표시된다.

### 시나리오 B: 회원 정지

- Given `ACTIVE` 회원 상세를 보고 있다.
- When 관리자가 `회원 정지`를 선택한다.
- Then 대상과 영향을 설명하는 확인 대화상자가 열리고 초기 포커스가 안전한 취소 동작에 놓인다.
- When 변경을 확정한다.
- Then 중복 제출이 방지되고 상태가 `SUSPENDED`로 갱신되며 성공 메시지가 발표된다.
- And 실패 시 상태는 `ACTIVE`로 유지되고 재시도할 수 있다.

### 시나리오 C: 시험 상태 확인

- Given 초안, 게시 예정, 진행 중, 종료, 보관 시험이 각각 존재한다.
- When 관리자가 시험 목록에 진입하거나 상태 필터를 선택한다.
- Then 서울 시간 기준 파생 상태가 올바른 텍스트 배지로 표시된다.
- And 기간이 없는 초안은 `일정 미설정`으로 표시된다.

### 시나리오 D: 시험 간편 등록 성공

- Given 관리자가 시험 간편 등록 화면에 있다.
- When 모든 필수 필드와 유효한 값을 입력하고 임시 저장한다.
- Then 단 한 건의 `DRAFT` 시험이 만들어진다.
- And 새 시험 상세로 이동해 입력한 값과 생성된 식별자를 확인할 수 있다.
- And 시험 목록에서 수정일 최신순 첫 결과로 확인할 수 있다.
- And 데모 모드에서는 새로고침 시 초기화될 수 있다는 안내가 보인다.

### 시나리오 E: 시험 간편 등록 실패

- Given 시험명 누락, 중복 코드, 시작보다 이른 종료 시간이 입력되어 있다.
- When 관리자가 임시 저장한다.
- Then 각 오류가 해당 필드와 상단 요약에 한국어로 표시된다.
- And 저장 요청은 성공으로 처리되지 않으며 현재 입력값이 유지된다.
- And 오류 요약과 필드 오류가 스크린 리더에 중복 혼란 없이 전달된다.

### 시나리오 F: 직접 URL과 권한

- Given 인증되지 않았거나 관리자 권한이 없는 사용자가 있다.
- When 해당 사용자가 메뉴를 통하지 않고 관리자 URL 또는 변경 엔드포인트에 직접 접근한다.
- Then 실데이터 구현에서는 401/403 또는 로그인/권한 부족 화면으로 처리된다.
- And 회원·시험 데이터가 RSC payload나 응답 본문에 포함되지 않는다.
- And P0 데모에서는 이 동작이 미구현임을 문서와 데모 배지로 분명히 한다.

| 상황 | 화면 처리 | 사용자 행동 |

| 필터 결과 없음 | 적용 조건 표시, 검색어 수정, `필터 초기화` | 조건 완화 |
| 목록 조회 실패 | 데이터 영역 오류, 원인 노출 금지, `다시 시도` | 재시도 |

| 401 | 로그인 필요 안내 또는 로그인 이동 | 로그인 |
| 403 | 권한 부족, 관리자 문의 안내 | 안전한 이전 화면 이동 |

예상 가능한 검증·조회 실패는 화면 상태로 모델링하고, 예기치 않은 예외만 `error.tsx` 경계에서 처리한다. `not-found.tsx`는 잘못된 상세 ID를 맡는다. 로딩 상태는 `loading.tsx` 또는 데이터 가까운 `Suspense` 경계를 사용하되, 관리자 셸 전체가 불필요하게 다시 로딩되지 않게 한다.

## 12. 반응형과 접근성 요구

### 반응형

- 기준 폭은 소형 `< 640px`, 중형 `640~1023px`, 대형 `>= 1024px`로 검증한다.
- 대형: 고정 폭 사이드 내비게이션과 유동 본문. 본문 최대 폭은 데이터 밀도에 맞추되 수평 스크롤을 최소화한다.
- 중형: 축소 사이드 내비게이션 또는 상단 메뉴, 핵심 표 열 우선 유지.
- 소형: 드로어 내비게이션, 표를 카드 목록으로 전환, 필터는 접이식 패널, 주요 버튼은 손가락으로 누르기 충분한 크기.
- Tailwind CSS 레이아웃은 프로젝트 규칙에 따라 `grid`가 아니라 `flex` 조합을 사용한다.
- 320px 폭에서도 본문이 잘리거나 전역 가로 스크롤이 생기지 않아야 한다.

### 접근성

- WCAG 2.2 AA를 목표로 텍스트 대비 4.5:1, 큰 텍스트 3:1, UI 경계·포커스 3:1 이상을 확인한다.
- 모든 입력은 보이는 `label`, 설명, 오류 연결을 갖고 필수 여부를 텍스트로 표현한다.
- 상태 변경, 저장 성공·실패, 결과 건수는 적절한 `aria-live` 영역으로 알린다.
- 대화상자는 제목·설명 연결, 포커스 트랩, Escape 닫기, 닫힌 뒤 트리거로 포커스 복귀를 제공한다.
- 표는 캡션 또는 주변 제목을 제공하고 열 머리글을 올바르게 연결한다. 모바일 카드는 읽기 순서가 시각 순서와 일치한다.
- 모든 상호작용은 키보드로 가능하고 포커스 표시를 제거하지 않는다.
- 아이콘 단독 버튼은 접근 가능한 이름과 툴팁을 제공한다.
- 상태는 색상에만 의존하지 않는다.
- Motion 사용 시 전환은 짧고 미묘하게 유지하며 `prefers-reduced-motion`에서 제거하거나 축소한다.
- 자동 초점은 오류 복구·대화상자 같은 명확한 경우에만 사용한다.

## 13. 데모 데이터 사양

### 데이터 규모와 구성

- 회원 24명: `ACTIVE` 16, `SUSPENDED` 5, `WITHDRAWN` 3
- 시험 15개: 초안 4, 게시 예정 3, 진행 중 3, 종료 3, 보관 2
- 이름·이메일·날짜·응시 횟수는 서로 달라 검색, 정렬, `null`, 0건을 검증할 수 있게 한다.
- 경계값 데이터: 최근 로그인 없음, 응시 0회, 100점 합격선, 일정 없음, 긴 시험명, 기간이 오늘 경계를 지나는 시험
- 현재 시간 의존 테스트가 흔들리지 않도록 `now`를 주입하거나 기준 시각을 고정해 파생 상태를 계산한다.
- ID와 시험 코드는 실행마다 동일한 결정론적 값으로 제공한다.

### 데모 변경 규칙

- 검색·필터·상세 조회는 데모 데이터 소스를 통해 수행한다.
- 회원 상태 변경과 시험 간편 등록은 브라우저 세션 또는 프로세스 메모리에 반영할 수 있다.
- 데모 변경은 영속성을 보장하지 않으며 화면 상단과 성공 메시지에 이를 알린다.
- 새로고침 초기화를 기능 오류로 보지 않되, 한 세션 안에서는 목록과 상세가 일관되어야 한다.
- 테스트는 초기화 함수 또는 새 브라우저 컨텍스트로 기준 데이터를 복원할 수 있어야 한다.

## 14. 실데이터 전환 경계

### UI가 의존할 계약

페이지와 컴포넌트는 배열 상수에 직접 접근하지 않고 아래의 서비스 계약에만 의존한다. 타입 이름은 예시이며 구현 시 `types/`, `services/`, `db/` 경계를 따른다.

- `listMembers({ query, status, cursor, limit }): MemberListResult`
- `getMember(id): MemberDetail | null`
- `changeMemberStatus({ id, fromStatus, toStatus, reason }): MutationResult`
- `listExams({ query, displayStatus, cursor, limit, now }): ExamListResult`
- `getExam(id): ExamDetail | null`
- `createExamDraft(input): CreateExamResult`

`MutationResult`는 최소 `ok`, `fieldErrors`, `formError`, 성공 시 변경된 DTO를 제공한다. 목록 응답은 `items`, `total`, 향후 `nextCursor`를 포함한다. UI에는 비밀번호 해시, 내부 메모, 삭제 토큰 같은 민감 필드를 전달하지 않는다.

### 단계별 교체

1. **P0 데모 어댑터**: 타입과 서비스 계약, 결정론적 인메모리 데이터, 검증 규칙을 제공한다.
2. **백엔드 계약 확정**: Elysia REST 요청·응답 스키마를 같은 DTO와 오류 모델에 맞춘다.
3. **DB 도입**: Neon PostgreSQL 테이블을 Drizzle 스키마와 마이그레이션으로 관리한다. raw SQL은 Drizzle로 표현할 수 없을 때만 사용한다.
4. **실서비스 어댑터**: 데모 어댑터를 Elysia 클라이언트 또는 서버 전용 DAL로 교체한다.
5. **보안·운영**: 인증, 역할 검사, 감사 로그, 관측성, 속도 제한, 동시성 제어를 활성화한다.

### API·DB에서 추가 결정이 필요한 항목

- 회원 이메일·전화번호 보존, 마스킹, 탈퇴 시 익명화 정책
- 시험 코드 생성 주체와 중복 충돌 정책
- 일정 경계의 포함 여부와 서버 기준 시간
- 회원 상태와 시험 상태 변경 감사 로그 스키마
- 페이지네이션 방식(cursor 권장)과 정렬 인덱스
- 낙관적 동시성 제어를 위한 `version` 또는 `updatedAt` 조건
- 인증 제공자, 세션 저장 방식, 역할 정의

## 15. Next.js 16.3 구현 원칙

- `src/app/admin/layout.tsx` 형태의 중첩 레이아웃으로 공통 셸을 구성한다.
- 페이지·레이아웃은 기본 Server Component로 두고 이벤트 핸들러나 브라우저 API가 필요한 작은 영역만 `'use client'` 경계로 분리한다. 큰 레이아웃을 Client Component로 바꾸지 않는다.
- 데이터 조회는 Server Component에서 서비스/DAL을 호출하며, 동적 데이터 가까이에 의미 있는 `Suspense` 폴백을 둔다.
- 변경은 Server Action 또는 Elysia REST API 중 팀 아키텍처 결정에 따르되, 양쪽 모두 입력 검증과 인증·권한 검사를 서버에서 수행한다.
- Server Action은 직접 POST 요청으로 호출될 수 있으므로 UI 노출 여부를 보안 수단으로 사용하지 않는다.
- 예상 오류는 구조화된 반환값으로, 예기치 않은 오류는 오류 경계로 처리한다.
- 성공 후 목록·상세 일관성을 위해 관련 경로 재검증 또는 최신 응답 반영 전략을 사용한다.
- 고유 페이지 제목과 `h1`을 제공해 Next.js 기본 경로 알림이 유용한 이름을 읽게 한다.
- shadcn/ui는 버튼, 입력, 셀렉트, 배지, 대화상자, 시트, 토스트, 테이블에 우선 사용하되 현재 미설치 상태이므로 구현 작업에서 명시적으로 추가한다.
- Motion은 드로어·상태 전환에만 제한적으로 사용하고 현재 미설치 상태이므로 구현 작업에서 추가 여부를 결정한다.

## 16. QA 체크리스트

### 기능

- [ ] `/admin`이 P0 시작 화면인 회원 관리로 이동한다.
- [ ] 회원 검색은 이름·이메일·회원 번호를 대상으로 하고 대소문자 차이로 결과가 누락되지 않는다.
- [ ] 회원 상태 필터와 검색을 함께 적용하거나 각각 초기화할 수 있다.
- [ ] 회원 상세에서 허용된 상태 전이만 노출되고 확인 후 목록·상세가 일치한다.
- [ ] 시험 검색은 시험명·코드를 대상으로 한다.
- [ ] 시험 파생 상태가 고정 기준 시각과 서울 시간에서 정확하다.
- [ ] 시험 간편 등록의 모든 필수값, 범위, 코드 형식, 중복, 날짜 순서를 검증한다.
- [ ] 빠른 연속 클릭으로 시험이 중복 생성되지 않는다.
- [ ] 등록 성공 후 상세와 목록에서 같은 값을 확인할 수 있다.
- [ ] 취소와 이탈 확인이 입력 손실을 방지한다.

### 상태와 오류

- [ ] 데이터 자체 없음과 필터 결과 없음이 서로 다른 문구와 행동을 제공한다.
- [ ] 목록 로딩, 조회 실패, 저장 실패, 404, 401, 403, 예기치 않은 오류를 각각 검증한다.
- [ ] 저장 실패 후 입력값과 기존 데이터가 보존된다.
- [ ] 오류 메시지에 스택, SQL, 개인정보가 노출되지 않는다.
- [ ] 데모 초기화 제약이 오해 없이 보인다.

### 반응형·접근성

- [ ] 320px, 375px, 768px, 1024px, 1440px에서 핵심 흐름을 완료할 수 있다.
- [ ] Tailwind 레이아웃은 flex 기반이며 전역 가로 스크롤이 없다.
- [ ] 키보드만으로 모든 메뉴, 필터, 상세, 대화상자, 폼을 조작할 수 있다.
- [ ] 포커스 순서와 표시가 논리적이며 대화상자 닫힘 후 원래 위치로 돌아간다.
- [ ] 각 페이지의 제목과 `h1`이 고유하고 경로 변경이 보조 기술에 전달된다.
- [ ] 입력 라벨·오류·설명이 프로그램적으로 연결된다.
- [ ] 상태와 오류는 색상만으로 전달되지 않는다.
- [ ] 200% 확대와 고대비, `prefers-reduced-motion`에서 내용과 기능이 유지된다.
- [ ] `bun run lint`의 접근성 규칙 경고가 없다.

### 품질·보안

- [ ] `bun run lint`가 통과한다.
- [ ] `bun run build`가 통과한다.
- [ ] 데모 시간·ID·정렬이 결정론적이다.
- [ ] 클라이언트 DTO에 민감 데이터가 포함되지 않는다.
- [ ] 실데이터 단계에서 직접 URL, Server Action, API 요청 모두 권한을 재검증한다.
- [ ] 변경 작업은 중복 요청과 동시성 충돌을 안전하게 처리한다.

## 17. 스크립트·의존성 영향

이 기획 문서 작성 자체로 `package.json`, `bun.lock`, npm/Bun 스크립트에 미치는 영향은 **없다**. 현재 검증 명령은 `bun run lint`, `bun run build`이며 별도 테스트 스크립트는 없다.

후속 구현에서는 shadcn/ui와 Motion, Elysia, Drizzle, Neon 연결 패키지가 필요할 수 있어 의존성과 lockfile 변경이 발생한다. 자동화된 수용 기준 검증을 위해 `test` 또는 `test:e2e` 스크립트 추가를 권장하지만 P0 기획 범위에는 포함하지 않는다. 패키지 관리자는 저장소 선언에 맞춰 Bun을 우선 사용하며, npm 명령을 별도로 추가할 필요는 없다.
